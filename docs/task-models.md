# 两种任务的状态模型

版本：0.5.1。日期：2026-10-29。

任务列表继续通过原有 HTTP、MCP 和快照接口读取。后台以 `mode` 区分两种记录，各自定义创建、状态、操作、校验和恢复规则；Manager 只分发操作并协调保存、授权取消及中断。

| 约定 | 多轮工作 | 原聊天额度监测 |
| --- | --- | --- |
| 模块 | `server/direct-task.js` | `server/monitor-task.js` |
| `mode` | `direct`，新建时明确记录 | `quota-wake` |
| 主要数据 | 原始目标 `prompt`、计划、输出和当前轮次 | 本地备注 `note`、续作消息和额度恢复发送记录 `wake` |
| 计数 | `rounds`，按 `maxRounds` 限制 | `sentCount`，按 `maxWakeSends` 限制 |
| 手动继续 | 重置执行轮次并等待调度 | 保留累计发送次数，重新开启监测 |
| 允许状态 | 排队、等待、启动、执行、授权、暂停中、暂停、阻塞、失败、完成 | 监测、等待、暂停、阻塞、结束并移除 |
| 执行通道 | Codex 轮次与授权协议 | 额度恢复后的消息队列；发送前检查原聊天回复 |

`server/task-model.js` 按模式选择规则，并保留共用字段的基本结构检查。Store 使用各模式的状态和计数校验；工作记录不能保存监测发送字段，监测记录不能使用执行、授权或启动等工作状态。轮次启动入口也会拒绝监测记录，其外部轮次通知不会写入计划、输出或授权映射。

两种模式仍使用现有的 `continuous` 字段以兼容界面和持久化格式，含义分别是“允许继续下一轮”和“开启额度监测”。状态及计数的规则由各自模块维护，调用方不再通过同一段分支处理两类任务的暂停、继续和完成。

通过挂件或完整页面加入原聊天时，可勾选「加入后开始监测」，与新记录一并保存；未勾选和 MCP 导入都保持暂停。开启监测不会改变后台调度开关，也不会因当前额度正常而立即发送消息，仍需确认后续耗尽与恢复。

## 旧数据与恢复

- 读取没有 `mode` 的旧工作记录时补为 `direct`，保留目标和执行次数。明确标为 `direct` 的 writer 等待继续按工作模式重试。
- 只有没有模式、满足历史 writer 冲突条件的旧记录才迁为监测；旧直接执行轮次不能当作已排队消息，其发送次数从 0 开始。
- 旧监测记录的 `prompt` 转为备注，缺少 `sentCount` 时按原有兼容规则读取旧计数；已有发送次数、备注和自定义消息继续保留。之后移除监测记录中的旧目标、轮次、计划、输出及执行轮次 ID。
- 缺少耗尽证据的待发送记录继续阻塞；重启时正在发送的记录转为结果不确定并保存，不自动重发。
- 恢复备份也先执行模式迁移，再关闭两种任务的自动推进。监测恢复不会新增工作执行字段。

数据 schema 继续为 1，使用现有字段与模式标记。迁移只在新源码运行时作用于其指定的数据目录；本轮测试使用独立数据，未安装或切换正在使用的版本。
